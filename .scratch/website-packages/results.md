# Package-template implementation and validation

Date: 2026-10-16. **Implemented and evaluated locally with live models.** Final run: `v3`, shared prompt version 11. Evaluation itself did not deploy, commit or push. The user subsequently authorised committing and pushing the implementation, private templates and this report.

## Delivered

Two standalone private Website templates, each in German and English, are linked
from [README](README.md). Prices, package responsibilities, correction rounds,
extras and care remain private configuration. The Creator chooses the purchased
template and edits only genuinely purchased extras/care before invitation.
Built-in thorough templates and existing frozen configurations were not changed.

The [live offer](https://drefrajo.dev/en/website) was read successfully over HTTPS
and checked on this date. In addition to the supplied agent brief, it specifies
one client-supplied launch article for the blog, 50/50 payment, 30-day defect
fixing and the prerequisites for the normal seven-working-day schedule. The new
private instructions include these; the old empty-blog/percentage-care terms
were not carried forward.

Generic Interview Policy now respects who prepares content: supplied-copy
services cannot silently become substantial copywriting, and included Creator
research/image work cannot become Client homework. Document/revision prompts
preserve that boundary and distinguish factual drafts, unperformed research,
pending delivery and approval before publication. Complete's research does not
run in this application; an actionable Creator task is the truthful output.

The concise handoff uses five parts: facts/action; supplied copy or in-scope
draft; design constraints/delegations; purchased scope/exclusions; owned next
tasks and delivery/launch checks. See [handoff format](handoff.md).

## Concept-description mismatch

New Client concept cards no longer display pre-render descriptions. Selection
and review use the actual image, identifying name and explicit keep/avoid
preferences. The exact server-stored confirmation excludes the pre-render
description and explains the image basis. Confirmed Creator/Markdown views do
not append another description as an agreed requirement. Other Creator concept
notes and exported concept Markdown label it as unverified planning material.

The upper-navigation/sidebar regression is covered in both languages, the real
server confirmation test, Client review and Creator/export presentation. Stored
historical confirmation summaries remain exact and are never rewritten. This
resolves the agreement ambiguity, not image-generator obedience to every prompt.

### Actual novice review and concept flow

Both fresh conversations were replayed through the real React Client page,
Convex actions/mutations, Agent storage and state transitions in a local test
database. After automatic arrival at document review, a separate Client model
independently chose actions from actual visible controls/text and image pixels.
The harness did not tell it which next-step button or concept to choose.

Each novice independently:
1. Reviewed the supplied-copy document or generated draft.
2. Clicked “Weiter zu den Konzepten”, then “Fortfahren”.
3. Compared three newly generated real PNGs.
4. Selected a direction and entered ordinary-language keep/avoid preferences.
5. Reviewed the selected image and exact preferences.
6. Explicitly confirmed the style and immutable submission.

Both tests passed; six screen decisions and three live generated images each.
Start's Client explicitly required own photos 01–04 and unchanged supplied copy.
Complete's Client asked for the email address to be directly readable and retained
the paid-licence restriction. Server-stored summaries match those preferences,
refer to the displayed image and contain no pre-render rationale. All six images
were also inspected manually; the alternatives vary in composition/type/palette.

This exercised actual UI components in jsdom, not a hosted browser or a human
usability study. Both Clients selected concept 1, so preference/order bias remains
possible. Neither rejected every concept; rejection, more-options and reference
paths retain deterministic UI/server coverage, not fresh human evidence.

## What the pilots changed

The initial seven completed handoffs averaged 993 words (817–1,158). Repetitive
contract/acceptance lists were drowning out the copy and next actions. The final
seven average **471 words (401–586)**, retaining complete copy, original Start
wording, gallery organisation, real exclusions and owned dependencies. This is a
descriptive pilot/final comparison, not a controlled timing study.

Other observed issues were fixed before the final run:
- Some documents promised concepts using files the app cannot see. Shared policy
  now explicitly distinguishes illustrative concepts from later original-asset
  inspection, and the final handoffs preserve that sequence.
- A pilot reply called a missing contact destination a later delivery task.
  Policy now explicitly requires a usable destination before alignment; both the
  final scenario and repeated-pressure probe held that boundary.
- Purchase terms in a factual checkpoint caused a simulated Client to reopen
  commercial agreement. The templates now confirm facts/action/delegation and
  document already purchased terms separately. Genuine objections still pause
  instead of being ignored. The final Client fixture explicitly knows it has
  purchased the package, as the requested scenario requires; an earlier fixture
  had omitted that context and invented a price dispute. Those paused pilot
  records remain available and are not counted as successful novice runs.
- A local assertion expected a street address known only to the private Client
  profile, not supplied to the interviewer. That expectation was corrected,
  with the original failed check preserved. Inventing the address would have
  been wrong. In the final run the Client did supply it and it was retained.

Earlier `v1` and `v2` records are preserved; final findings above use `v3` only.
The exact final private instructions were checked against every final recording.

## Remaining work and limits

The Client still must supply essential business facts and a usable main action,
approve final public content and consciously choose a style. Start additionally
requires finished copy and organised assets; the preparation checklist does not
make absent content implementation-ready. Complete still requires the Creator to
do its included research and image/rights work outside this app. Later content
changes, supplied legal texts and publication prerequisites remain real duties.

Generated concepts are illustrative: details and decorative marks are not new
scope or a promise of an exact layout/logo. Excluding pre-render descriptions
resolves contradictory approval text; it does not guarantee image generation
follows every prompt detail.

Real-human completion time, comprehension and style satisfaction remain
unvalidated. The 5–10-minute goal needs a human pilot; fewer turns or a model
choosing an attractive image alone cannot establish that goal.

## Reproduction

The following runners and fictional fixtures remain local and are intentionally
excluded from the implementation commit. Recording links above also refer to
ignored local evidence, not files shipped with the application.

Live runners require a privately acquired development credential in the temporary
file used by the runners. Never commit it; remove it after testing.

```sh
bun .scratch/website-packages/run.ts --run=my-new-run
bun .scratch/website-packages/check-recordings.ts my-new-run
PACKAGE_EVAL_RUN=my-new-run bunx vitest run --config .scratch/website-packages/ui.config.ts
bun .scratch/website-packages/probes.ts --run=my-new-run
bun .scratch/website-packages/summarize.ts my-new-run
```

Use a fresh run name for new prompts/instructions rather than replacing this
evidence. The final command also removes the temporary credential. These manual
tests are excluded from the ordinary test suite and production build.
